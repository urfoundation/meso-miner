## Transport

- **A silent platform edge no longer drains egress through proxied H3** **[redeploy]** (commit `23a7741c4`, direct to `main`). With `h3` set to `all`, a count or `auto`, every proxy identity runs the H3, H3-over-dns and dns-pump carriers beside its H1. When the edge answers nothing, each carrier redials on its own 30 to 60 second timer and every dial runs the whole QUIC retransmit ladder, about 33 KB. One node on `h3 all` spent a flat 15.5 to 16.4 Mbit/s for about 15 hours of the 2026-10-23 outage, roughly 30 times more tx than rx, while the governor read `verdict=ok rate=200.0/s`. Three things hid it, and each is fixed: QUIC bytes were never charged to the connect attempt, so the failed-byte breaker saw zero; a canceled dial (two of every three, because the per-transport H3 gate cancels a lower-priority carrier when a better one waits) was dropped with its bytes; and H3 dials never waited on the attempt budget. The handshake's wire bytes are now charged once, a canceled attempt's bytes count toward the breaker without counting as an attempt, and a proxied identity's H3 waits on the shared budget like its H1. The direct identity, proxy index 0 and family-pinned transports never wait. Nodes on the default `h3 direct` were not affected.

## Extender, blocker and fingerprint

- **The v2026 extender stack, the blocker gate and the switchable Chrome ClientHello** **[redeploy]** ([#39](https://github.com/urfoundation/meso-miner/pull/39)). This brings the 3.23-fix port to this line as one stacked change. The extender v2 library and server replace the old server, with a provider serving role that is opt-in (`URNETWORK_EXTENDER`): it takes the direct slot, listens on tcp 443, then quic 443 and dns 4053, authorizes forwards from the hosts in `URNETWORK_EXTENDER_ALLOWED_HOSTS`, and adds the pinned directory candidate. The blocker is now consulted in the packet path before egress route decisions, and the host lookup happens only after an IP miss; tests cover IPv6, UDP, mid-connection and setter races. A fingerprint drift harness gates the dialers' ClientHello and QUIC Initial against a synthetic golden. The Chrome ClientHello is off by default: `urnet-tools set tls-hello on|off` flips it live and `URNETWORK_TLS_HELLO` sets the startup default. Four dataplane leaves arrive with it: egress TTL realism (inactive at the zero mode), H3 datagram auth compatibility, a request-scoped HTTP redirect policy and DoH dial observation. Docs conflicts were resolved in favour of this line's newer H3 documentation.
- **The extender review findings are fixed** **[redeploy]** ([#40](https://github.com/urfoundation/meso-miner/pull/40), [#41](https://github.com/urfoundation/meso-miner/pull/41), [#42](https://github.com/urfoundation/meso-miner/pull/42)). The feed read deadline is set before the cancel hook, so a canceled read is not blocked by a deadline set afterwards. A zero connect timeout stays unbounded on H3, matching the TCP carrier helpers, and an unbounded H3 connect aborts when its context ends. Issued-key pruning walks the table only when the epoch changes. Counts from retired servers fold into the cumulative counters after the server has drained, and a second retire of the same server no longer folds twice. A VLESS response header resumes after a read timeout without resending the request header, and finishes before a read error is reported, so a read that returns the final header bytes together with an error does not lose the payload. A dial or feed read now waits for a cancel callback that has already started, so a connection is not handed out just before the callback closes it.
- **The extender relay counter test no longer depends on segmentation** **[no redeploy]** ([#43](https://github.com/urfoundation/meso-miner/pull/43)). The test pinned one read per write, but the same session can report four ingress reads on one run and three on another. Byte counts stay exact and read counts are bounded between one per chunk and one per byte.

## Observability

- **`urnet-tools proxy trim` reports the cap in force** **[redeploy]** ([#33](https://github.com/urfoundation/meso-miner/pull/33), [#35](https://github.com/urfoundation/meso-miner/pull/35)). With no argument it used to refuse to run. It now prints the trim cap and its source (operator, OOM or thrash), the configured pool before the cap, how many proxies the cap holds back, and the running counts when the provider answers. The cap is read from the provider snapshot first, so an unreadable `proxy_trim` file cannot hide a cap the provider enforces; the file is used when the provider is stopped or predates the fields. `urnet-tools status` carries the same information as a `trim` row on the live block whenever a cap applies, and `status --json` gains `configured`, `trim_cap` and `trim_cap_source`. The provider records the selection only when `proxy_url.json` was readable, because an unreadable cache would understate the pool, and a `trim_reported` flag separates an empty pool from a provider that does not report trim state.
- **The lifetime counters say when they began** **[redeploy]** ([#36](https://github.com/urfoundation/meso-miner/pull/36), [#38](https://github.com/urfoundation/meso-miner/pull/38)). The lifetime lines printed totals with no start date, so a store that began this morning looked the same as one counting for months. The store persists a `since` stamp written once, and the `[lifetime]` and `[pqe]` all-time lines print `all-time (since ...)`, the `since-start` figures print the process start, and `/metrics` exports `urnet_lifetime_start_timestamp_seconds` and `urnet_lifetime_start_approximate`. A store written before this change keeps its totals, is pinned to the load time and says `start approximate, totals include earlier history`. A follow-up fixes a real bug in that migration: it never marked the store dirty, so an idle node re-pinned a later date on every restart. A year-one stamp now loads as unknown instead of an exact date. The trailing `(since-start ...)` on the health line stays where it was so log parsers that match the current order keep working.
- **The disk benchmark measures a sustained rate** **[redeploy]** ([#51](https://github.com/urfoundation/meso-miner/pull/51), [#53](https://github.com/urfoundation/meso-miner/pull/53)). It stopped at a fixed 16 MiB, which an NVMe writes in about 20 ms, so the verdict was right but the number was a burst. The 3 second budget governs now: a slow microSD still trips the 1 second early exit at about 20 MiB, an eMMC at about 80 MB/s writes about 240 MiB, and an NVMe stops at the 256 MiB ceiling in about 85 ms. The startup line carries the duration, for example `900.0 MB/s (256 MB written in 85 ms)`. The container guard (`URNETWORK_DISK_BENCH=1` to force), the IO-pressure skip, the free-space cap, the cache TTLs and the hung-write watchdog are unchanged. The cache entry records its sampling shape, so a `disk-bench.json` written by the old sampler is a miss and is not reused for 24 hours.
- **The PSI figure appears** **[redeploy]** ([#44](https://github.com/urfoundation/meso-miner/pull/44)). The reader asked for a resource named after the line, which does not exist, so `psi_some_avg60` was dropped from every sample on every node. It reads the memory resource now, and a test pins the resource name.

## Provider reliability

- **The url-sourced warmup hold is bounded to five minutes** **[redeploy]** ([#37](https://github.com/urfoundation/meso-miner/pull/37)). Warmup is declared done only above 90% of registered proxies up with fewer than 5 connecting, and the count includes proxies that never authenticate. On one production node the ratio sat at 85 to 88% and the only exit was the 60 minute backstop: each restart held newly qualified URL proxies behind dead file proxies while the running pool drained from 481 to 420, and the URL fetcher parked on the same flag. The hold now ends 5 minutes after process start, and the reload gate and fetcher share one predicate. The file ramp still gets its uncontested window.
- **A thrash restart is not reported as a rejected sign-in** **[redeploy]** ([#49](https://github.com/urfoundation/meso-miner/pull/49)). Exit code 75 has two producers: a failed sign-in quarantines the child, and the thrash watchdog or liveness self-exit plans a restart. The supervisor knew only the first. A planned restart now writes a one-shot `thrash_exit.<pid>` marker beside `thrash_cap.json` just before it exits, and the supervisor consumes it for the pid it reaped. Only the operator log line changes: both branches make the same state changes, the automatic sign-in backoff comes from the set-aside files on disk, and exit 75 is unchanged, so systemd, the container start scripts and OpenRC still restart on it. An earlier mtime-based design was dropped because a mid-life write of `thrash_cap.json` could hide a real quarantine. `docs/Troubleshooting.md` lists both producers.
- **A failed OOM cap state write is reported** **[redeploy]** ([#52](https://github.com/urfoundation/meso-miner/pull/52), [#54](https://github.com/urfoundation/meso-miner/pull/54)). The startup decision wrote its state and discarded the result. The state carries the cap and the clean-window clock, so a lost write left an unwritten cap enforced by nothing, or a stale window that could relax the cap straight after a fresh OOM kill. Both branches report the failure now, and the applied path leaves the timeline at the last cap that was really persisted. The warning names the clean-window clock only when it moved, because a clean start with no standing cap loses nothing.
- **A hotkey wallet write completes on Windows** **[redeploy]** ([#45](https://github.com/urfoundation/meso-miner/pull/45)). After the rename, the write flushed the parent directory, and Windows answers that with access denied, so a write already in place was reported failed. Both the originals chain and the pending statement use this path. The flush goes through `internal/durablesync`, which keeps the directory precondition and absorbs only the errnos that mean the platform has no directory flush; Unix does the same fsync as before. The PR author checked a wallet write on a Windows host.

## Installer

- **The installer refuses unsafe paths and bad binaries** **[installer]** ([#44](https://github.com/urfoundation/meso-miner/pull/44)). A symlinked service home or state dir is refused as the first statement of `do_install`, before the download, because root's mkdir and chmod would otherwise land somewhere else. A binary that is not a non-empty executable is refused before it replaces a working one, since a truncated download produced a provider that failed at exec time after the old binary was already renamed away. The release tag is read with jq, then python3, then a sed fallback, so a clean FreeBSD host, which has no python3 in base, no longer fails and blames the GitHub API. Later commits in the PR cover the install tree in the symlink guard, re-check the state dir at the point of the root write, replace the version file instead of following it, accept a staged binary that only lost its exec bit, and say when the tool digest cannot be verified.
- **The PATH hint is never written through a symlinked shell rc** **[installer]** ([#46](https://github.com/urfoundation/meso-miner/pull/46), [#48](https://github.com/urfoundation/meso-miner/pull/48)). The FreeBSD installer appended a PATH line to the service user's rc and then ran chown on it, as root, in a directory that user owns, and both operations follow a symlink. A planted link at `.profile` sent root's append and ownership change into a file of the attacker's choosing. [#46](https://github.com/urfoundation/meso-miner/pull/46) refused a symlinked rc and replaced the file by rename; [#48](https://github.com/urfoundation/meso-miner/pull/48) supersedes it because root still reopened the path by name. The whole edit now runs as the service user through `su -m`, with the script on stdin, and root only maps the exit status (0 wrote, 10 already present, anything else warns and the install continues). Three smaller defects are fixed with it: a commented-out PATH entry no longer suppresses the hint, a file with no trailing newline no longer gets the line glued on, and a failed append no longer replaces the rc with a half-written temp. The regression test lifts the block into a sandbox; the PR reports 14 cases failing against the pre-fix installer.

## Deploy notes

- **Redeploy the provider** for the H3 fix, the extender stack, the trim and lifetime reporting, the warmup bound, the thrash marker, the disk benchmark, the OOM cap warning and the PSI field. An old process keeps the old behaviour.
- **Run the installer** on nodes that should get the symlink guards, the binary checks and the PATH hint fix. `urnet-tools` is delivered by the installer.
- **The extender role is opt-in** (`URNETWORK_EXTENDER`) and the Chrome ClientHello is off until `urnet-tools set tls-hello on` or `URNETWORK_TLS_HELLO` is set. Neither changes a node that sets nothing.

## Caveats

- The H3 fix has not been run against a live outage. The attempt budget floor is 2 per second, so a throttled node still spends about 0.5 Mbit/s, not zero.
- The extender stack is a port; its production behaviour on this line has not been observed. Egress TTL realism is inactive at the zero mode.
- The counters are lifetime totals. A provider restart starts the process-scoped figures at zero again, so compare rates, not absolute values across a restart. A legacy store's start date is approximate.
- GitHub Actions is disabled on this repository, so the CI changes above have not run here.
